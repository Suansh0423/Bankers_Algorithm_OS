Banker's Algorithm Core Foundations

1. Origin & The Banking Analogy

Developed by Edsger W. Dijkstra in 1965, the Banker's Algorithm is a deadlock avoidance algorithm. It is named after a conservative small-town banker who never allocates available cash in such a way that he can no longer satisfy the maximum credit claims of at least one customer.

2. Essential Data Structures

  • Available[m]: If $Available[j] = k$, there are $k$ instances of resource type $R_j$ available.
  • Max[n][m]: If $Max[i][j] = k$, process $P_i$ may request at most $k$ instances of $R_j$.
  • Allocation[n][m]: If $Allocation[i][j] = k$, process $P_i$ is currently allocated $k$ instances of $R_j$.
  • Need[n][m]: Remaining resource need: Need[i][j] = Max[i][j] - Allocation[i][j]

3. The Safety Algorithm

1
Let $Work = Available$ and $Finish[i] = false$ for $i = 0, 1, \dots, n-1$.
2
Find an index $i$ such that both:
a. $Finish[i] == false$
b. $Need_i \le Work$
If no such $i$ exists, go to Step 4.
3
$Work = Work + Allocation_i$, $Finish[i] = true$. Go to Step 2.
4
If $Finish[i] == true$ for all $i$, then the system is in a safe state.

4. Time Complexity Analysis

For $n$ processes and $m$ resource types:
• In the worst case, finding a process takes $O(m \cdot n)$. Repeating for all $n$ processes gives $O(m \cdot n^2)$.

Top University Viva Voce Questions

Deadlock Prevention enforces constraints by eliminating at least one of the 4 Coffman conditions (Mutual Exclusion, Hold & Wait, No Preemption, Circular Wait) ahead of time. This often leads to low resource utilization.

Deadlock Avoidance (like Banker's Algorithm) dynamically inspects every resource request with prior knowledge of maximum claims to ensure the system never enters an unsafe state.

No! An unsafe state is NOT necessarily a deadlock. An unsafe state only means that the OS cannot guarantee that deadlock will not occur if all processes simultaneously demand their maximum claims. However, if processes release resources early or don't request their full max, deadlock might still be avoided.

  • Processes must know and declare their maximum resource requirements in advance, which is rarely realistic.
  • Number of processes and resources must remain fixed dynamically.
  • Substantial runtime overhead of running an $O(m \cdot n^2)$ safety check on every single resource request.
  • Resources must not fail or crash while held by processes.
  1. Mutual Exclusion: At least one resource must be held in a non-shareable mode.
  2. Hold and Wait: A process must be holding at least one resource and waiting to acquire additional resources.
  3. No Preemption: Resources cannot be forcibly taken from a process holding them.
  4. Circular Wait: A closed chain of processes exists where each process holds resources needed by the next.

If $Request_i \le Need_i$ is true, but $Request_i > Available$, process $P_i$ must wait because the requested resources are currently unavailable. No state modification or safety check is executed until resources are freed.

A sequence of processes $\langle P_0, P_1, \dots, P_{n-1} \rangle$ is a safe sequence if, for each $P_i$, the resources that $P_i$ can still request can be satisfied by currently available resources plus resources held by all preceding processes $P_j$ ($j < i$).

Yes, a system can have multiple valid safe sequences depending on which eligible process executes first.
